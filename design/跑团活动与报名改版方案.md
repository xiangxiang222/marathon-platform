# 跑团活动与报名改版方案

本文定义跑团内部训练与约跑的创建、浏览和报名体验。活动报名表达“我准备参加”，不代表付款、比赛报名资格或保险保障；赛事发现和官方赛事报名仍沿用赛事产品流程。文中描述的是设计目标，未接入的能力列为后续，不作为当前已有功能展示。

## 目标与边界

组织者应能在短流程内写清活动时间、集合点、训练安排和组别；成员应能先判断是否适合，再主动选择组别并确认报名。Web 与微信小程序字段、状态和说明保持一致，差异只来自浏览器控件与微信原生日期、时间选择器。

本方案覆盖跑团活动列表、活动详情、发布训练/活动、成员报名和基本隐私规则。活动仅在现有跑团成员访问权限内展示。比赛赛事仍是公开赛事目录中的独立对象：用户可标记想跑或已报名，正式报名由组委会页面承接。

## 信息层级与页面结构

活动列表按“即将开始 → 已结束 → 已取消”组织，默认优先显示近期活动。活动行先显示日期和标题，再显示类型、地点、距离与报名人数；次级状态使用短文本标签。管理员看到“发布活动”主入口，普通成员只看到浏览、报名和自己的报名状态。日期筛选、状态筛选与标题搜索放在列表上方，默认收起不常用筛选。

活动详情按以下顺序展示：

1. 活动标题、训练类型、日期时间、地点和报名状态。
2. 集合时间与集合点、计划距离、路线说明。
3. 报名组别、已报名人数/容量和活动安排。
4. 参与须知、取消报名截止时间及必要的安全提示。
5. 活动相册和组织者工具；管理操作放在次级区域。

首屏主按钮随状态变化为“选择组别报名”“取消我的报名”或不可操作的真实状态说明。已满、已截止、已结束和已取消分别标记，不把它们统一成模糊的“不可报名”。

## 组织者创建流程

跑团管理员从“跑团 → 训练/活动 → 发布活动”进入。普通成员不显示创建入口；无权限访问创建页时显示明确说明并返回跑团。

### 第一步：选模板

选轻松跑、长距离、间歇跑或自定义类型，并填写活动标题。模板仅用于带入标题提示和活动类型，不自动生成虚假的课程、路线或配速。提供“从往期活动复制”入口，但复制前说明会复制哪些内容。

### 第二步：时间与地点

填写活动日期和开始时间、活动地点、具体集合点。结束时间、集合时间、计划里程、期次和路线说明为可选项；报名截止与取消截止默认留空，表示按活动开始时间管理。Web 使用日期时间输入，小程序使用原生选择器。前端与服务端都校验结束时间不能早于开始、截止时间不能晚于开始。

### 第三步：分组与安排

至少保留一个可报名组别；每组填写组名、配速或目标和名额，名额为零代表不限。成员报名时自行选择，不由系统按个人资料自动分配。补充训练安排、参与须知及路线提示；较少使用的积分或成团参数放入“更多设置”，并注明实际生效规则。

填写完成后进入独立的发布前预览：按成员看到的层级展示日期、地点、组别、容量和训练说明，提示必填项及组别冲突，再由管理员确认发布。预览不是额外的数据填写步骤。发布成功后直接进入活动详情。

### 草稿和复制规则

草稿按“跑团 ID + 当前账号”隔离，Web 存在当前浏览器、小程序存于当前设备；草稿提示所属跑团、保存时间和设备范围。恢复与删除由用户明确选择，不跨跑团、跨账号自动恢复，也不声称跨设备同步。

复制活动只带入可复用内容：类型、标题、地点与集合点、路线、训练安排、须知和组别设置。必须清空活动开始/结束时间、报名与取消截止、报名名单、签到、相册、活动状态及历史计数；复制后先提示“日期和报名状态已清空”，要求组织者重新核对再发布。复制流程不覆盖该跑团的未完成草稿。

## 成员报名流程

成员从跑团活动列表打开详情，查看活动时间、地点、报名截止、组别配速和剩余名额，再进入报名页。存在多个组别时必须主动选择一个；没有分组时明确显示“本场不分组”。已满组不可选，不默认切换其他组，也不加入候补名单。

昵称使用当前账号资料，不在报名页修改。性别和跑步水平可选填，并说明用于现场协调、仅本人和活动组织者可见；不要求手机号、住址、健康史或紧急联系人。活动名单对跑团成员显示昵称、所选组别和领跑标记，服务端不会向其他成员返回性别或跑步水平；管理者视图可读取这两项资料。隐私边界由服务端响应落实，不依赖前端隐藏。

确认页复述活动名、时间、集合点、所选组别和截止规则，主操作为“确认报名”。提交后根据服务端结果显示“报名已确认”或具体失败原因；不展示虚假的付款、退款、保险购买或票券状态。取消报名提示只说明报名状态或名额会怎样变化，不提“退款”。

现有活动 `review` 字段用于活动相册内容审核，不等同于新成员报名审核。Web 与小程序统一使用“相册内容需审核”这一语义；报名结果不得因为该开关显示为待审核。若未来要增加报名审批，须另有服务端状态和管理流程后再单独设计。

## Web 与微信小程序适配

| 场景 | Web | 微信小程序 |
| --- | --- | --- |
| 活动列表 | 桌面端内容区限宽，列表信息列对齐；小屏单列卡片，筛选可折叠。 | 保持一列卡片，使用原生日期/时间和导航能力，底部导航空间不遮挡列表。 |
| 活动详情与报名 | 桌面端正文与报名摘要可并列；窄屏改为单列，主按钮固定在内容底部区域。 | 单列展示；底部操作考虑安全区，返回后保留活动详情上下文。 |
| 创建 | 进度条显示三步，桌面日期与地点字段可两列排布，预览页信息完整。 | 字段默认单列，使用原生选择器；底部固定“保存草稿 / 上一步 / 继续或发布”，避开安全区。 |
| 状态反馈 | 表单错误贴近对应字段，提交结果可读且可重试。 | 使用页内提示与轻量 Toast；不可只用 Toast 表达权限、容量和日期校验错误。 |

320px、390px、平板和桌面宽度均应检查标题换行、组别人数、固定底部操作与长文本；不以缩小正文解决溢出。表单标签、错误和可选状态保持清晰，不依赖颜色单独表达。

## 视觉方向

沿用平台品牌色：主色红 `#ff0a30`、页面灰 `#f5f6fa`、卡片白 `#ffffff`、主文字 `#1f2026`。红色用于当前步骤、主要操作和重要状态；日期、人数、配速等内容以黑灰层级呈现，容量已满和错误同时使用文字说明。

活动类型使用简洁文字标记，避免把每个类别做成一张彩色大卡。配速组使用清楚的名称、目标和名额行，报名选择用稳定尺寸的单选项。跑道视觉采用代码绘制的细线椭圆跑道与少量红色分道标记，可用 CSS/WXML-WXSS 复用；只作为小型品牌标记，不使用大幅背景图、照片或与路线数据无关的装饰。

## 能力边界与后续

本轮不设计候补名单、周期重复排期、活动付费、保险购买或内置即时通讯。满组直接显示已满；重复活动由管理员逐场创建或使用日期已清空的复制；活动本身不收费；保险信息不伪装为承保声明；联系与通知继续沿用产品当前已存在的渠道，不承诺站内聊天、自动群消息或推送。独立分享海报也不列入本轮。

跑团活动报名不修改赛事目录、赛事官方报名链接或个人赛事状态。赛事详情可以标记“已报名”，其含义仍是用户自我记录；只有组委会平台确认的结果才是正式参赛报名。

## 验收标准

1. Web 与小程序的创建字段、三步顺序、报名状态、可选信息说明和取消提示一致。
2. 每个组别都显示容量规则；满组禁止选择，服务端再次校验容量和截止时间。
3. 草稿不跨跑团或账号恢复；复制活动清空所有日期、报名、签到、媒体和状态数据。
4. 报名必须显式选择组别；可选资料可不填，提交后不会出现费用、退款或保险状态。
5. 活动成员名单与可见资料经服务端权限核验，非成员不能通过接口访问名单。
6. `review` 明确表示相册审核；页面不将其显示成报名审核。
7. 验证管理员、普通成员、游客/无权账号、满组、截止、取消、失败重试等状态；覆盖 320px、390px 与桌面布局。
